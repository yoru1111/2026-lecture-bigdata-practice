# Observations

## Task 1
Confidence is not symmetric: on the bench data (support 50), 1468 → 0 has confidence 0.84 but 0 → 1468 only 0.004, because item 0 is in 65% of all baskets while 1468 is rare; only "1468 → 0" is a claim worth stating, and even that one is weak (next line).
The highest-confidence rule is 1468 → 0 (0.84), but its lift is 1.28: item 0 is so common that nearly anything "predicts" it, so I don't believe it describes a relationship. The rule I do believe is 270 ↔ 252: confidence only 0.24 / 0.23 but lift 15.1 (73 shared baskets), which looks like one of the planted pairs. On the hand-made baskets, diaper → beer is the same story: confidence 0.8, lift 1.12.
With 2,000 items brute force needs 2,000·1,999/2 = 1,999,000 pair counters. After pass one at support 50 only 1,849 items survive, so A-Priori needs at most 1,849·1,848/2 = 1,708,476 counters (triangular matrix), and only 820,259 of those pairs actually occur and got a counter.

## Task 2
It never became unbearable on my laptop (Ryzen 5 7430U, 13.8 GB RAM): even support 1 took 12.5 s and 334 MB. Time ran out "first" in the sense that it grew most (1.4 s → 12.5 s); memory stayed far from the ~2 GB free. Counters hit a ceiling of 893,456 at support 25, where all 2,000 items are frequent and every pair that occurs at all is counted, so this data set simply runs out of pairs.
A4: while pass one still filters (400 → 50), counters grew 5.5×, 4.7×, 3.0× per halving — worse than doubling, because frequent items grow ~2.3× per halving and pairs grow with the square of that.
A5: frequent pairs grew a steady 2.5–3× per halving, so from 400 to 50 answers grew 26× while counters grew 77×; at support 50, 99.2% of counters were for pairs that were not frequent. "Just a slightly lower threshold" therefore costs far more memory than it returns in answers — the cost is candidates, not answers.

## Task 3
I used 1,000,003 buckets (a prime): pass one hashes 3.43 M pair occurrences (893 k distinct pairs), so the average bucket gets ~3.4 hits against a support of 50 and most infrequent buckets stay infrequent. Result: identical 6,397 pairs, peak counters 820,259 → 23,356 (97.2% cut, "strong").
R5, honestly: the bucket array is 1 M × 4 B = 4.0 MB during pass one. In textbook bytes, the baseline's pass two is 6.8 MB (triangular matrix, 1,708,476 × 4 B) and PCY's pass two is 0.13 MB bitmap + 23,356 triples × 12 B = 0.4 MB, so PCY's peak is 4.0 MB vs 6.8 MB — a 1.7× saving, mostly memory moved from pass two into pass one. (In Python objects the gap is bigger: tracemalloc peak 107.9 MB vs 4.7 MB, because each dict counter costs ~130 B.) Re-running on prefixes of the data with support scaled and 1 M buckets fixed: 2,500 baskets PCY loses (4.0 vs 2.6 MB), 5,000 is break-even (4.0 vs 4.3 MB), 10,000+ wins (4.0 vs 6.6 MB). The crossover depends on how many frequent items survive pass one (baseline cost grows ~ their square) versus how many buckets you need to keep the average bucket load well below the support (~pair occurrences / support). I also found that building the array with `array("I", bytes(4*B))` briefly held a second copy and doubled the peak (8.3 MB); `array("I", [0]) * B` fixed it.
Smaller bucket arrays: 250 k buckets → 38,941 counters (95.3% cut); 62.5 k → 329,571 (59.8%, average load 55 > support, so many buckets are frequent by accident); 15.6 k → 820,259 (0% — every bucket is frequent and the bitmap passes everything). 4 M buckets → 7,683 counters (99.1%), but the array itself is 16 MB, which is worse than the 1 M choice.
